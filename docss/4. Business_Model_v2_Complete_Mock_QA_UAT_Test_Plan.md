# 1. Test Objective

The test programme must prove all of the following before production activation:

- old monetary Invite/Royalty, old bands/cycles, old combined Loyalty 3-slot logic and the old 4% cap are inactive;
- Project-specific Direct/Loyalty/Trip settings are versioned and immutable after approval;
- the Booking Request version Accounts ultimately approves freezes the exact commercial/reward rules;
- Direct, Customer Loyalty, Trip, Reference, Royalty Gift and Buying Commission each follow their own milestones;
- Buyback reward qualification uses the 25% source-payment gate and Stable Buyback Completion correctly;
- non-cash reward states are not treated as monetary `PAID` commissions;
- Recovery, deactivation, nominee, staff-conflict and circumvention holds work without deleting entitlement history;
- accepted commercial risks are implemented exactly as approved rather than silently “fixed”;
- Dashboard, Member Portal, reports, scheduled jobs, audit and permissions agree with the underlying domain state;
- retries and concurrent events cannot create duplicate entitlements.

---

# 2. Test Levels

| Level | Purpose | Minimum evidence |
|---|---|---|
| **Unit** | Pure rule/calculation/state-transition functions | automated assertion |
| **Integration** | Database constraints, services, transactions, scheduled jobs | automated test + database assertion |
| **E2E QA** | Screen/workflow behaviour across roles | screenshots/video + record IDs + audit evidence |
| **UAT** | Business-user confirmation that behaviour matches approved policy | signed Pass/Fail with tester/date |
| **Go-Live Regression** | Final production-like validation after migration/reseed | release evidence pack |

A P0 case must pass at Unit/Integration where technically applicable and at E2E/UAT where the behaviour is user-visible.

---

# 3. Severity / Priority

| Priority | Meaning |
|---|---|
| **P0** | Wrong result can create money/reward loss, duplicate entitlement, security/privacy breach or incorrect go-live rule. No open P0 defects at sign-off. |
| **P1** | Important workflow/task/report defect. Must be fixed unless MD signs a documented release exception. |
| **P2** | Cosmetic/non-blocking issue with no business-rule impact. May be deferred with owner approval. |

---

# 4. Execution Rules

1. Run business-rule cases against a clean v2 reward seed or isolated test namespace.
2. Do not use old Invite/Royalty mock records as live prerequisites.
3. Every test-created Booking, Acquisition, benefit, Trip Credit, Royalty Credit and task must have a unique test reference.
4. Payment percentages must be verified through the same service/workflow used by the application; do not directly edit database totals for UAT.
5. Where a test needs a correction, use the real correction workflow so audit/history is tested.
6. For concurrency tests, run two transactions at the same logical time and inspect database uniqueness/locking results.
7. Every P0 UAT case captures: record IDs, frozen Version ID, current state, audit event, task outcome and report/portal outcome where applicable.
8. All timestamps are checked in Asia/Kolkata.
9. A test passes only when both the business state and user-visible state are correct.
10. If source rules are ambiguous, stop the case and raise a numbered Change Request; do not invent behaviour.

# 28. Standing Integrity Queries / Assertions — Must Return Zero Exceptions

The implementation team should provide automated reconciliation queries/assertions for at least these invariants:

1. Approved Booking without frozen `projectSettingsVersionId`.
2. Approved Project Version with `effectiveAt < approvedAt`.
3. Direct rate >5% or Loyalty rate >3%.
4. Same Booking with both current Direct and current Customer Loyalty sale-side benefit.
5. More than one current monetary benefit record for same Booking/type/beneficiary role.
6. More than 3 current valid Customer-closing Loyalty events for one Person.
7. More than one consumed lifetime Reference opportunity for one introduced Member.
8. More than one Royalty Credit for one Royalty opportunity.
9. More than one Own-Sale Credit for same Member + Plot/Unit + Programme identity.
10. One Trip Credit used by more than one reward.
11. Qualified Buyback-route reward where source Payment Received was <25% at qualification.
12. Buyback-qualified Trip/Gift fulfilled before Stable Completion unless the Royalty source independently reached 100% where allowed.
13. Delivered Gift with Royalty opportunity reopened.
14. Travelled Trip with its used Reference/credit opportunity reopened.
15. Expired credit marked Used in a later reward after expiry.
16. Deactivated Member with new Customer Loyalty event earned while Deactivated.
17. Active Member recorded as Sold By Customer.
18. Customer closer without qualifying own purchase/KYC/Terms.
19. Non-family nominee fulfilled without required MD approval.
20. Staff/relative benefit fulfilled/paid without conflict approval.
21. Multiple unrelated Persons sharing one verified bank account without approved joint-account exception.
22. Recovery Circumvention hold bypassed before review decision.
23. Old monetary Invite/Royalty record created after v2 Effective Date.
24. Old Invite/Royalty cycle/position state affecting an entitlement after v2 Effective Date.
25. `Commission Conflict — Above 4%` generated after v2 Effective Date.
